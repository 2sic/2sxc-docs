# Changes to the Dev Environment in v22.01

The current `develop` version is **22.01.00**.
This guide covers updating an existing development installation by building and copying files without running the 2sxc installer.
For the initial setup, see [Contribute to 2sxc / EAV](xref:Abyss.Contribute.Code.Index).

The ILogger integration upgrades the DNN logging dependencies from 2.1.1 to 8.0.0.
Copying the new DLLs alone does not update the DNN host's assembly binding redirects.
Apply the following steps even if you continue using Legacy logging.
Installing or upgrading the 2sxc DNN module ZIP normally updates these redirects through the DNN installer; a Debug build does not run that installer.

## 1. Prepare the Existing Environment

1. Back up the development site's `web.config`, deployed 2sxc files and database so you can restore the previous environment.
1. For DNN, use **DNN 10.1 or later on .NET Framework 4.8**, as required by the current module manifest.
   Upgrade an older DNN host and 2sxc module through its normal upgrade process before deploying the current development build.

The current source requires the **.NET 10 SDK** to build the modern targets and build tools. DNN itself still runs on .NET Framework 4.8.

## 2. DNN: Build and Update the Assemblies

1. Restore NuGet packages and build the DNN project, `2sxc/Src/Dnn/ToSic.Sxc.Dnn/ToSic.Sxc.Dnn.csproj`, in **Debug** using your configured development build.
   This also builds its EAV and 2sxc project references. The Debug copy step deploys to the website configured in `DnnTargets` in `2sxc-build.config.json` (for example, `D:/Projects/2sxc/2sxc-dnn/Website`).
1. Verify these four DLLs in the **DNN website's `bin` folder**:

   | Assembly | NuGet package version | Assembly version | File version |
   | --- | --- | --- | --- |
   | `Microsoft.Extensions.Logging.dll` | 8.0.0 | 8.0.0.0 | 8.0.23.53103 |
   | `Microsoft.Extensions.Logging.Abstractions.dll` | 8.0.0 | 8.0.0.0 | 8.0.23.53103 |
   | `Microsoft.Extensions.Options.dll` | 8.0.0 | 8.0.0.0 | 8.0.23.53103 |
   | `Microsoft.Extensions.Primitives.dll` | 8.0.0 | 8.0.0.0 | 8.0.23.53103 |

   These are the versions supplied by the current 2sxc DNN build for the DNN 10.1 baseline.
   The installation manifest uses **file versions**; binding redirects use **assembly versions**.

> [!IMPORTANT]
> A newer DNN host may already supply newer Microsoft.Extensions assemblies.
> Preserve the host's compatible dependency set and redirects; do not overwrite newer host DLLs with the 8.0.0 copies or redirect them back to 8.0.0.0.
> The XML in the next step applies when the deployed assemblies are version 8.0.0.0.
> The Debug copy step does not reconcile binding redirects.

### Other Logging Dependencies

The current manifest and packaging rules already cover the other ILogger dependencies, including
`Microsoft.Bcl.AsyncInterfaces`, `System.Diagnostics.DiagnosticSource`, `System.Memory`,
`System.Numerics.Vectors` and `System.Runtime.CompilerServices.Unsafe`.
DNN 10.1 supplies DependencyInjection 8, `System.Threading.Tasks.Extensions` and `System.Buffers` through its own dependency packages.
No additional DLL entry was identified as missing from the ILogger dependency graph for that baseline.

Keep the existing `bin/2sxc` placement and `codeBase` configuration for `Microsoft.Bcl.AsyncInterfaces`.
Do not move isolated dependencies into the website's root `bin` as part of this update.

The explicit `Microsoft.Extensions.Logging.Abstractions` package references in `ToSic.Sys.Core` have been removed because `Microsoft.Extensions.Logging` supplies them transitively.
This does **not** remove the runtime dependency: `Microsoft.Extensions.Logging.Abstractions.dll` is still required.

### Missing Configuration DLLs During Build

`Microsoft.Extensions.Logging` 8 no longer brings in `Microsoft.Extensions.Configuration`,
`Microsoft.Extensions.Configuration.Abstractions` or `Microsoft.Extensions.Configuration.Binder` as transitive dependencies.
Older DNN packaging and development copy rules still listed these files, causing `MSB3030` errors after a clean build.

Use the updated `ModulePackage.Targets`, `AfterBuild.Targets` and DNN manifest from the current development source.
If Visual Studio still reports the old copy errors, reload the DNN project so it picks up the changed target files, then rebuild.
Do not add package references or copy old DLLs just to satisfy the obsolete entries.
Imageflow's separately packaged `Configuration.Abstractions` dependency remains in place.

### System.Buffers Must Match the DNN Baseline

DNN 10.1 already supplies `System.Buffers` **4.6.0**; newer hosts may supply a newer version.
The DNN project references 4.6.0 for compilation with `ExcludeAssets` set to `runtime`, as it does for host-provided DependencyInjection assemblies.
The 2sxc installation manifest, Release packaging and Debug copy rules no longer include `System.Buffers.dll`.
This preserves the host's DLL and binding redirect.

Previously, NuGet could resolve the older transitive minimum **4.5.1**, while the 2sxc manifest declared the newer DLL.
An installation could then copy an older DLL and update its binding redirect to that older assembly version.

| NuGet package | Assembly version | File version |
| --- | --- | --- |
| 4.5.1 (older transitive minimum) | 4.0.3.0 | 4.6.28619.01 |
| 4.6.0 (DNN 10.1 baseline) | 4.0.4.0 | 4.600.24.56208 |
| 4.6.1 (newer host version) | 4.0.5.0 | 4.600.125.16908 |

After updating the source, restore and rebuild the DNN project.
Reload the DNN project in Visual Studio to pick up the updated target files.
The rebuilt 2sxc installer must not contain `bin/System.Buffers.dll` or declare it as an assembly in the manifest.
A stale DLL left in a local build output must not be included in the installer or copied to the site.

If a development site was already downgraded, stop its application pool, back up the current DLL and `web.config`,
then restore the host's original `System.Buffers.dll` and set the active `System.Buffers` redirect to its actual assembly version.
For the DNN 10.1 baseline this is **4.0.4.0**; if the host already used 4.6.1, preserve **4.0.5.0** instead.
Restart the site and verify page rendering and the content editor.
Do not lower an existing newer host DLL or redirect to the baseline version.

## 3. DNN: Update web.config Binding Redirects

Edit the **DNN website's** `web.config`.
Inside the existing `<configuration><runtime><assemblyBinding xmlns="urn:schemas-microsoft-com:asm.v1">`,
replace the active entries for the following four assemblies with these values when using the 8.0.0.0 DLLs:

```xml
<dependentAssembly xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity name="Microsoft.Extensions.Logging" publicKeyToken="adb9793829ddae60" />
  <bindingRedirect oldVersion="0.0.0.0-32767.32767.32767.32767" newVersion="8.0.0.0" />
</dependentAssembly>
<dependentAssembly xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity name="Microsoft.Extensions.Logging.Abstractions" publicKeyToken="adb9793829ddae60" />
  <bindingRedirect oldVersion="0.0.0.0-32767.32767.32767.32767" newVersion="8.0.0.0" />
</dependentAssembly>
<dependentAssembly xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity name="Microsoft.Extensions.Options" publicKeyToken="adb9793829ddae60" />
  <bindingRedirect oldVersion="0.0.0.0-32767.32767.32767.32767" newVersion="8.0.0.0" />
</dependentAssembly>
<dependentAssembly xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity name="Microsoft.Extensions.Primitives" publicKeyToken="adb9793829ddae60" />
  <bindingRedirect oldVersion="0.0.0.0-32767.32767.32767.32767" newVersion="8.0.0.0" />
</dependentAssembly>
```

Keep exactly one active `dependentAssembly` entry per assembly in this binding section.
Comment out or replace older 2.1.1/2.2 entries and remove obsolete `codeBase` mappings for these four assemblies that point to copies under `bin/Imageflow`.
Preserve unrelated entries and the existing assembly-binding section.

If the host supplies newer versions, use their actual assembly versions and preserve its compatible configuration instead of applying the example above.
The redirects and the deployed DLLs must agree.

## 4. Oqtane: Update Through the Existing Development Build

1. Restore and build the Oqtane projects with the **.NET 10 SDK** against an **Oqtane 10.2+ host on .NET 10**.
   Use the existing Oqtane development copy configuration to update the module and its 2sxc/EAV assemblies.
   Oqtane supplies logging through the ASP.NET Core shared framework, and `DiagnosticSource` is part of the .NET runtime.
1. Restart the application after updating the module files.

The platform-neutral EAV library still declares its own logging compile dependencies.
The presence of logging in the host does not replace those project references.

## 5. Optional: Enable Microsoft.Extensions.Logging

Legacy remains the default logging stack.
Enabling MEL is a separate development choice and is not required to complete the assembly update.

For DNN, merge this entry into the existing `<appSettings>` section in the website's `web.config`:

```xml
<add key="Logging:2sxc:UseMel" value="true" />
```

For Oqtane, merge this property into the existing `Logging` section of the host's `appsettings.json`:

```json
{
  "Logging": {
    "2sxc": {
      "UseMel": true
    }
  }
}
```

Restart the application after changing the setting.
To return to Legacy, set it to `false` and restart.
See the [logging roadmap](xref:Abyss.Releases.Epics.Logging) for configuration details and current limitations.
